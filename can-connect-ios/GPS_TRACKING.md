# GPS routes with scanner recordings

Automatic and manually started scanner recordings now start the iPhone's Core Location recorder alongside OBD polling. Both streams belong to the same saved trip. Connect → Devices → This iPhone shows location status during scanner recording as well as phone-only recording. The existing screens, card layout, colours and soot percentage are unchanged.

For an automatic scanner trip that begins while locked or another app is open, Always location authorization is required. In Connect → Devices, tap the existing This iPhone card to request it; Precise Location should be enabled. While Using remains supported for sessions started with DriveLine open, and those sessions can continue into the background. The app does not silently upgrade authorization.

Location permission is required for routes; denied/revoked location access does not end an MX+ recording. That session continues with its measured vehicle readings, and a temporary message explains why GPS is missing. Phone-only GPS retains its existing permission/error behaviour. Finish and scanner loss stop GPS after the recording is durably saved. App switching checkpoints the same draft and leaves location updates running using the existing location background mode. iOS still controls background launch and execution; force-quitting cannot be overridden.

GPS fixes must be fresh, obtained since this recording's location updates began, and have horizontal accuracy within 50 metres. Recorded points reject backwards/duplicate timestamps and implausible jumps. Map lines break across gaps over 30 seconds. Scanner distance remains integrated from measured vehicle speed; GPS points do not add distance again. Phone-only distance is calculated from consecutive valid GPS points. No missing coordinates are inferred from speed or filled from a map.

The local recording/archive retains coordinates, accuracy, timestamps and available GPS speed. Mac uploads include both the raw scanner responses and separate GPS samples. The Mac retains the exact original upload and imports the coordinates and vehicle signals into its trip. GPS speed is not labelled as ECU vehicle speed. Old scanner recordings that contain no coordinates cannot acquire a historical route from this fix.

Validation includes injected scanner/GPS lifecycle tests, permission failure, background checkpoint, save/reload/export, distance isolation, delayed callback timestamps, and route gaps. The UI test drives Core Location with explicitly synthetic coordinates while a TCP scanner fixture supplies OBD data, switches to the Home Screen, then checks the saved route map. Mac tests and an isolated receiver integration test verify mixed GPS/OBD uploads, coordinates, receipts, deduplication and original preservation.

Physical acceptance remains a new drive with the iPhone and MX+: allow location and Precise Location, confirm GPS active before departure, then check the saved route and its Mac copy once parked. Software simulations do not verify GPS reception in the actual car or a full locked-screen drive.

## Background-start correction (build 21)

Three real drives transferred byte-for-byte to the Mac: 16,823 scanner responses and 379 GPS points. The foreground-started drive retained 378 route points; subsequent background-started trips retained one and zero. The user confirmed those later trips began while locked or using another app. The originals on the phone have the same gaps, so transfer is not their cause.

Build 21 adds the Always usage description and an explicit permission action on the existing This iPhone card, preserving its layout. With While Using and no existing location session, a background start remains pending with an accurate status; foreground activation starts GPS for that same scanner recording. Always permits starting successive trips in the background. A permission interruption retains recording intent so granting access can resume an ongoing scanner trip. Finish clears that intent, preventing location collection from restarting afterward. Seven GPS and seven scanner lifecycle tests passed, including background-start gating, foreground resumption, successive Always-authorized background trips and explicit permission upgrade. Signed device build passed. A new physical drive starting while locked with Always access is still required; these changes cannot reconstruct missing historical routes.

Apple documents the authorization distinction in [Requesting authorization](https://developer.apple.com/documentation/corelocation/requesting-authorization-to-use-location-services). Pelican's [first-drive handbook](https://pelican.clutch.engineering/handbook/first-drive/welcome) likewise requires Always for trips started while closed. Its [trip logger documentation](https://pelican.clutch.engineering/features/trip-logging) describes motion, CarPlay and OBD triggers. These public descriptions inform behavior comparisons; they are not access to Pelican's private implementation. DriveLine currently triggers automatic trips from scanner readings, not motion or CarPlay.

Build 21 was installed after a fresh checkpoint showed no active recording; all 32 saved trips, vehicle profiles, transfers and regeneration baseline match the pre-update backup. Launch initially required the user to unlock the phone. Always authorization and a new background-started physical drive still need confirmation.

The existing user-exported Pelican 5.1.1 (920) scanlogs contain two sessions with first standard speed responses 10.81 and 6.32 seconds after the first logged command. They explicitly select `ATSP6`, read identity and scan controller capabilities. Those are measured scanner-command timings from those exports, not total Bluetooth connection time or proof of Pelican's motion/arrival thresholds. No private logs, coordinates or vehicle identifiers are included here.
